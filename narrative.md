### 3.1 AI-Hub — `production`
**Oneliner:** Корпоративный SSO-портал и инфраструктурное ядро экосистемы

**Метрики:**
- OAuth2 — + PKCE + OIDC
- ADFS — корпоративная интеграция
- CI/CD — GitHub Actions

**Задача:** Разрозненные инструменты без единой авторизации. Каждый сервис — отдельный вход. Отсутствие контроля доступов и аудита использования.

**Решение:** OAuth2 Authorization Server с PKCE. Интеграция с Active Directory (ADFS/OIDC). AI-чат (Gemini streaming), каталог приложений, система промптов, admin-панель с RBAC.

**Результат:** Единая точка входа для всей экосистемы. Полный аудит действий. Управление пользователями, группами, доступами. Автоматический деплой через GitHub Actions.

**Tech:** FastAPI async, React 19, TypeScript, PostgreSQL, OAuth2/PKCE, ADFS/OIDC, JWT, Docker, Nginx, GitHub Actions

---

### 3.2 Автопротокол — `production`
**Oneliner:** ML-система автоматического протоколирования совещаний

**Метрики:**
- 7 — этапов ML-пайплайна
- 90+ — языков транскрипции
- 3 — бизнес-домена

**Задача:** Ручное протоколирование совещаний. Администратор проекта тратит значительное время на расшифровку, структурирование и распределение поручений.

**Решение:** Многоэтапный ML-пайплайн: транскрипция (WhisperX) → диаризация спикеров (pyannote) → анализ эмоций (wav2vec2) → структурирование и генерация артефактов (Gemini).

**Результат:** Кратное сокращение времени подготовки протоколов. Автоматическая генерация риск-брифов. Пилотируется на проектах. Три конфигурации: строительство, HR, IT.

**Tech:** FastAPI, Celery, Redis, WhisperX, pyannote, wav2vec2, Gemini, CUDA/GPU, React, Docker

### 3.3 CostManager — `production`
**Oneliner:** AI-аналитика себестоимости строительства и бенчмаркинг объектов-аналогов

**Метрики:**
- ~8 — пользователей (отдел)
- P10/P90 — статистический анализ
- Decimal — финансовая точность

**Задача:** Ручной анализ строительных смет. Классификация позиций вручную. Сравнение объектов-аналогов в разрозненных таблицах Excel.

**Решение:** AI-автоклассификация сметных позиций (Gemini + Ollama). Иерархическая разбивка затрат с дефлятированием. Генерация аналитических Excel-отчётов с P10/P90.

**Результат:** Департамент экономики строительства полностью перешёл на инструмент. Профессиональные отчёты: титульный лист, сравнительный анализ, попарное сравнение, рыночная валидация.

**Tech:** Python, Flask, PostgreSQL, Gemini API, Ollama, xlsxwriter, NumPy, Chart.js

### 3.4 DataBook — `production`
**Oneliner:** Интеллектуальный поиск по базе предписаний строительного контроля

**Метрики:**
- 8 500+ — уникальных предписаний
- ~25 000 — исходных записей
- ежедневно — используется инженерами

**Задача:** Инженеры СК тратят значительное время на поиск прецедентов предписаний в разрозненных источниках. Нет единой структурированной базы.

**Решение:** NLP-система с лемматизацией русского языка. Дедупликация через векторную близость (25 000 → 8 500). Полнотекстовый поиск PostgreSQL с fuzzy matching.

**Результат:** Ежедневно используется инженерами на объектах. Organic adoption: внедрение без административного давления. Поиск прецедента — секунды вместо часов.

**Tech:** Python, FastAPI, PostgreSQL FTS, NLP, Vector Similarity, React, Docker

## 4. Approach

### 4.1 Блок «Как я делаю продукты» (Methodology)

**Бейдж:** `КАК Я ДЕЛАЮ ПРОДУКТЫ`
**Заголовок:** От задачи до рабочего инструмента
**Подзаголовок:** Код перестаёт быть ограничением — им становится разрыв между бизнесом и реализацией. Знание домена позволяет проектировать архитектуру напрямую, без цепочки согласований.

**01 — Выявление узких мест:**
> Снимаю требования напрямую у участников процесса — без цепочки «аналитик → архитектор → разработчик».

**02 — Rapid Prototyping:**
> За пару недель — месяц — от архитектуры до работающего прототипа. Приоритет — скорость доставки до пользователя, а не идеальная кодовая база.

**03 — Валидация:**
> Продукт приживается естественным путём. Если MVP не решает реальную задачу ежедневно — гипотеза убивается, не сжигая бюджеты.

**04 — Масштабирование:**
> Успешный прототип переводится на единую инфраструктуру: SSO, ролевой доступ, переиспользуемые сервисы — без технического долга.

### 4.2 Блок «Почему это работает» (Business Value)

**Бейдж:** `ПОЧЕМУ ЭТО РАБОТАЕТ`
**Заголовок:** Что даёт совмещение отрасли и разработки

**01 — Time-to-Market: недели, не кварталы**
> Единая инфраструктура с SSO и переиспользуемыми сервисами — новый продукт стартует с готовой платформы, а не с нуля.
**Метрика:** Единая платформа — масштабируемый фундамент

**02 — Domain Oracle: решения без посредников**
> Архитектурные решения принимаются на стыке домена и кода — без промежуточных звеньев и потери контекста.
**Метрика:** Минимум согласований — максимум итераций

> 🚧 *Обсуждали переделать → «Из сущностей, не из экранов». Ждёт применения после кросс-анализа.*

**03 — Fail Fast: дешёвая проверка гипотез**
> Нерабочая идея убивается за недели, а не после миллионных вложений. Масштабируется и переводится в production только то, что приносит измеримый результат.
**Метрика:** Без CAPEX и кварталов ожидания

### 10.1 Фрейм «Конвейерный инженер» — основной

#### 10.1.1 Архитектура агентного конвейера
**Источник:** `C:\qq_project\dev\emb2\pipeline\README.md` + 9 под-папок с `README.md`, промптами `.md`, кодом, датасетами.

- **9 изолированных шагов конвейера:** parse_rtf → load_to_db → classify_chunks → classify_prescriptions → extend_taxonomy → decompose_violations → eval_search → eval_ot_e2e → generate_reports.
- **Каждый шаг — самодостаточная папка**: код + промпт + README + (опционально) датасет. Единственный общий модуль — `pipeline/_shared/` (config, metrics, cache, harness).
- **Промпты версионированы рядом со своим шагом**, не разбросаны по кодбейсу.
- Backend (`backend/`) не зависит от `pipeline/` — разделение «runtime API» и «агентный конвейер знаний».

#### 10.1.2 Экономия стоимости LLM как архитектурное решение
**Источник:** `pipeline/_shared/cache.py`, `pipeline/extend_taxonomy/` (поле `migration_strategy`), `pipeline/classify_chunks/harness.py`.

- **Трёхслойный кэш:** pickle-эмбеддинги Gemini / батчевая обработка (20–100 записей) / selective LLM-покрытие **только изменённых** данных (не всей базы при апдейте).
- **Стратегия `sql_keyword`:** теги обновляются через SQL по ключевому слову без обращения к LLM — экономия на больших наборах.
- **`migration_strategy` обязателен** для каждого нового тега, предлагаемого `extend_taxonomy`: указывается способ бэкфилла (SQL / LLM-дельта / синонимы). Без стратегии тег не принимается.

#### 10.1.3 Eval-first дизайн
**Источник:** `pipeline/eval_search/`, `pipeline/eval_ot_e2e/`, `workdir/eval_runs/report_2026-04-17.html`, `pipeline/_shared/metrics.py`.

- **Каждый шаг конвейера имеет привязанную метрику**, метрики считаются через унифицированный `harness.py` — деградация качества видна сразу.
- **Golden dataset:** 465 валидированных пар «суб-нарушение ↔ пункт НТД» с экспертной проверкой и эмбеддингом 3072D.
- **Отдельная выборка:** 88 production-кейсов OT.

#### 10.1.4 Измеряемое качество (prod-прогон 2026-04-17, 88 кейсов / 192 цитаты)
**Источник:** `workdir/eval_runs/report_2026-04-17.html`.

- **R@30 = 90.9%** — правильный пункт в топ-30 (пул для LLM).
- **Target-exact = 75%** — модель выбрала ровно тот пункт, что в golden.
- **«В тему» = 96.6%** — хотя бы одна полезная ссылка.
- **Галлюцинаций = 0%** — ни одной ссылки на несуществующий пункт (по Claude-судье).
- **Rank 1 = 56.8%** — первый ответ верный.
- **Средняя позиция target = MRR 0.499** — target в среднем на 2-й позиции.
- **~5 сек на запрос** (decompose → find-norms → generate).

#### 10.1.5 Grid-search и ablation как рутинная практика
**Источник:** `workdir/eval_runs/after_*.json`, `after_crosscat_*.log`, `claude_judge_*.json`.

- **96 конфигураций реранкеров** протестированы (cosine baseline, RRF, weighted sum, multiplicative, normalized). **RRF k=20 — победитель**, baseline +3% R@30; в 21.5% кейсов поднимает target с rank > 100.
- **Парадокс weighted-sum:** хуже baseline (−4.1% R@30) когда теги не заполнены — зафиксирован, проанализирован.
- **Cross-encoder ablation:** Gemini 2.5 Flash пересортирует top-50. Отдельно +2.5% R@30, в комбинации с RRF **best-of union = 78% R@30 / ≈81% от потолка**.
- **Multi-query retrieval:** LLM переформулирует запрос в 3 варианта → мультипулинг → RRF. +3% R@30, +8pp R@1 для OT. Pool miss: 13% → 3.7%; потолок recall 96.3%.

#### 10.1.6 Систематический разбор неудач, не вайб
